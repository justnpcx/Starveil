# 19 · 网关指纹（B1）设计说明

> 状态：**设计稿，无代码**。按任务书要求先给"采集什么、存哪儿、怎么用"，再决定是否实现。

## 1. 要解决的问题

场景自动化现在按"当前网络"切换策略，但网络的身份是**Wi-Fi SSID + BSSID**。这有两个毛病：

- 同名 SSID 到处都有（`CMCC`、`Starbucks`），BSSID 又会随 Mesh 漫游变化；
- 换到有线/热点时没有 SSID 可比。

网关指纹要回答的是：**"我是不是又在同一个出口后面？"** —— 与 SSID 无关，换 AP、换 Mesh 节点都还认得出。

## 2. 采集什么（只取"出口的形状"，不取内容）

| 字段 | 来源 | 为什么是它 | 稳定性 |
|---|---|---|---|
| 网关 MAC 的 OUI（前 3 字节） | ARP 表 | 区分路由器厂商，不暴露完整 MAC | 高（同型号设备一致） |
| 默认网关 IP | 路由表 | 192.168.1.1 / 10.0.0.1 这类习惯很强 | 中 |
| 网关开放的 DHCP 服务器标识 | DHCP OFFER 的 option 54 | 家用路由几乎必发 | 高 |
| DHCP option 55 的参数请求列表 | 本机发出 | 各家固件的默认序列不同 | 中 |
| DNS 服务器集合 | `LinkProperties` | 运营商/自建 AdGuard 一眼可分 | 中 |
| 门户探测 URL 与响应 | `/generate_204` | 酒店/机场会重定向 | 低（仅公共网） |
| 网关管理页的 TLS 证书 CN/颁发者 | 443 探测 | 厂商指纹（小米/华硕/OpenWrt） | 中（需一次探测） |

**明确不采集**：任何 HTTP 内容、任何账号、任何设备列表、任何流量特征。

## 3. 存哪儿

- **只存本机**：Room 表 `gateway_fingerprints`（id、指纹哈希、用户起的名字、首次/最近出现时间、命中次数）。
- 指纹本身存**哈希**（对拼接串做 SHA-256 后取前 16 字节），不存原始字段——这样即使数据库泄露也还原不出"这个人在哪"。
- **不上传、不参与备份导出**（备份里只保留用户给场景起的名字与规则，不保留指纹）。
- 保留策略：最近 90 天未命中的条目在启动时清理。

## 4. 怎么用

1. **场景匹配**：场景条件从"SSID 等于 X"扩展为"SSID 等于 X **或** 指纹命中 Y"。命中优先级低于显式 SSID。
2. **提示而非自动**：新指纹第一次出现时，只在场景页顶部提示"这是一个新网络，要给它建场景吗"，不自动切换策略——错误的自动切换比不切换更糟。
3. **诊断**：日志页可显示"当前指纹：`a3f1…`（已知：家）"，用于排查"为什么策略没生效"。

## 5. 隐私与合规边界

- 指纹是**网络设备**的属性，不是人的属性；哈希后无法反查具体地址。
- 采集全部发生在本机，不需要新权限（ARP/路由/DHCP 信息在 `ConnectivityManager` 与 `LinkProperties` 里已有；管理页探测需要一次 TLS 连接，仅在用户开启该场景功能时发生）。
- 与 `docs/10-privacy-policy.md` 的"不收集、不上传"一致；若将来要做云端规则共享，必须先把哈希盐值改为每设备随机，且明确写入隐私政策。

## 6. 实现前的三个待定问题

1. Android 10+ 拿不到 ARP 表（`/proc/net/arp` 受限），OUI 可能只能靠 DHCP option 12/60 的 hostname/vendor class 近似——需要一次真机验证。
2. 网关管理页探测会触发路由器日志，属于"主动行为"，是否默认关闭？
3. Mesh 网络里"网关"可能是漫游后的节点，指纹会抖动——需要"最近 3 次一致才算命中"的窗口。
