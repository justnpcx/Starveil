# 四款 Android 代理客户端基准对比（P3，定稿，未开工）

> **状态：定稿。** 这是 P3 公开阶段的获客材料，前置门禁是 M6 / M7 完成，且 M4 的
> PSS 数字已经落到 `docs/11-device-verification.md`。门禁之前不测、不写、不发。

## 目的

用可复现的数字回答「为什么是 Starveil」，而不是用形容词。报告只写测量结果、方法和
限制；不写「碾压」「吊打」这类判断。

## 对比对象

| 应用 | 版本（执行时记录） | 备注 |
|---|---|---|
| Starveil | 当前 release tag | 被测对象 |
| NekoBox | 执行时最新稳定版 | sing-box 系 |
| Hiddify | 执行时最新稳定版 | sing-box 系 |
| v2rayNG | 执行时最新稳定版 | Xray 系 |

版本号、安装包来源（GitHub Releases / F-Droid）必须写进报告。四个应用使用**同一个
节点、同一份订阅、同一个协议**，否则数字不可比。

## 指标与定义

| 指标 | 定义 | 采集方式 |
|---|---|---|
| 冷启动 TTID | 点击图标到首帧可见 | `adb shell am start -W <pkg>/.MainActivity` 的 `TotalTime`，10 次取中位数，每次前 `am force-stop` |
| 1000 节点滑动掉帧率 | 节点列表滚动时的 janky frame 比例 | 导入 1000 节点订阅，固定脚本滑动 20 次，`dumpsys gfxinfo <pkg> framestats` 统计；报告总帧数、janky 帧数、比例 |
| 常驻空闲 PSS | 连接后静置 5 分钟的总 PSS | `dumpsys meminfo <pkg> \| grep "TOTAL PSS"`，3 次取中位 |
| 单 GB 吞吐与发热 | 下载 1 GB 的平均速率、耗时、电量变化、最高温度 | 同一 HTTP 源、同一节点；`dumpsys thermalservice` 与 `dumpsys battery` 前后各一次；注明是否边充边测 |

所有指标都在**同一台设备、同一 Wi-Fi、同一时段**采集。设备型号、Android 版本、SoC、
内存容量写进报告；测试前开飞行模式 10 秒再恢复，清掉后台应用。

## 方法学（可复现）

1. 设备恢复出厂网络状态：飞行模式开关一次，确认无残留 VPN。
2. 按固定顺序安装四个应用，每个应用测完 `am force-stop`，不卸载（卸载会改变 ART 状态）。
3. 每个应用导入同一份 1000 节点订阅，选中同一节点，协议一致。
4. 每个指标重复 3 次（TTID 10 次），记录原始值，报告取中位数。
5. 原始数据以 CSV/JSON 放进 `docs/benchmarks/<date>/`，报告正文只放汇总表。
6. 测试脚本（滑动、计时、采集命令）一并放进同一目录，任何人可以照着重跑。

## 报告结构

1. 设备与环境（型号、系统、网络、节点、协议）。
2. 方法（上面的步骤，逐条）。
3. 结果表：四个应用 × 四个指标。
4. 观察：只写数字之间的关系（例如「A 的 TTID 中位数比 B 低 120 ms」），不写评价。
5. 限制：单设备、单网络、单节点；不代表所有地区/运营商；测试期间的版本号。
6. 附录：原始数据与脚本。

报告里的 Starveil PSS 必须与 `docs/11-device-verification.md` 的 M4 数字是同一组

再给数字；不允许两份文档各说一套。
